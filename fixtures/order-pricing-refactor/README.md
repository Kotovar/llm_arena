# Refactor order pricing without changing behavior

Категория Refactoring, сложность Medium. Промпт —
[docs/benchmark/prompts/03.md](../../docs/benchmark/prompts/03.md).

Модуль расчёта стоимости заказа: скидки клиента, промокоды, потолок скидки, доставка, сборы.
`calculateOrderTotal` корректна, но написана одной функцией на сотню строк с изменяемыми
переменными, вложенными условиями и магическими числами. Задача — навести порядок, не
изменив ни одного результата.

Деньги — целые центы, чтобы равнозначный рефакторинг не расходился с исходником из-за
плавающей точки. Единственный источник округления — `Math.round(amount * pct / 100)`; другая
формула процента может дать расхождение в цент, и это считается изменением поведения.

Зависимостей нет: TypeScript исполняет сам Node, тесты — на `node:test`. Интерфейса нет:
судится патч.

## Состояние fixture

| Проверка | Ожидание |
| --- | --- |
| Существующие тесты | `pass` |
| Поведение совпадает с исходным (скрытая) | `pass` — и до модели, и после правильного рефакторинга |

Обе проверки проходят с самого начала: это задача на сохранение поведения, а не на его
исправление. Упавшая скрытая проверка после модели — `wrong-solution`. Прошедшая — ещё не
PASS: решает ревью патча.

Сверяется командой `./scripts/verify-fixture order-pricing-refactor`.

## Что проверяет скрытая проверка

`validation/pricing-reference.ts` — замороженная копия исходной функции со своими типами,
чтобы не зависеть от того, что модель сделает с `src/`. Скрытый тест сравнивает с ней
20 000 заказов из детерминированного генератора (пороговые цены, регистр и пробелы в
промокодах, пустые заказы) и девятнадцать именованных комбинаций: VIP с промокодом, потолки
скидок, пороги доставки и сборов, округление. Плюс неизменность входа и публичный API:
`calculateOrderTotal`, `formatReceipt`, `formatMoney` из `src/index.ts`, и та же функция из
`src/calculateOrderTotal.ts`.

Проверено на мутантах эталона: сложенные проценты вместо последовательных, `>` вместо `>=`,
потолок скидки до промокода, промокод без `trim`, порог FLAT5 от неверной суммы, `floor`
вместо `round`, потерянный ранний выход для пустого заказа, упаковка без потолка — каждый
роняет хотя бы один тест.

## Что оценивать вручную

- **PASS** — функция заметно понятнее: части расчёта разделены, пороги и ставки названы,
  порядок «скидка клиента → промокод → потолок → доставка → сборы» читается из кода.
- **constraint-violation** — изменён API, типы, тесты или `receipt.ts`.
- **incomplete** — код почти не изменился.
- **Переусложнение** — классы-стратегии, фабрики и реестры правил для пяти условий. Эталон
  (`solution/calculateOrderTotal.ts`) обходится пятью функциями.

```bash
cp solution/calculateOrderTotal.ts fixture/src/calculateOrderTotal.ts   # во временной копии
```
