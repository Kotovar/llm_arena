# Fix incorrect permission propagation

Категория Code Understanding, сложность Hard. Промпт —
[docs/benchmark/prompts/06.md](../../docs/benchmark/prompts/06.md).

Права пользователя проходят четыре слоя, как в промпте, но на чистых ES-модулях вместо
React:

```text
src/api/userApi.js          ответ API как есть: роль бывает в старом формате (ROLE_EDITOR, Admin)
src/auth/rolePermissions.js роль → права; effectivePermissions учитывает блокировку
src/auth/normalizeUser.js   ответ API → пользователь приложения        ← причина здесь
src/store/authStore.js      текущий пользователь, can(permission)
src/ui/userActions.js       кнопки по store.can                        ← здесь симптом
```

`normalizeUser` приводит роль к каноническому виду, но права считает по **сырой** роли и
без учёта статуса. Поэтому учётки старого формата остаются без прав, а заблокированные
получают полный набор. Правильная функция — `effectivePermissions` — уже есть рядом и
покрыта тестами; она просто не используется.

Эталонная правка — две строки в `normalizeUser`: роль нормализуется один раз, права берутся
через `effectivePermissions(role, raw.status)`.

## Состояние fixture

| Проверка | Ожидание |
| --- | --- |
| Существующие тесты | `pass` — обычные роли в каноническом формате работают |
| Права верны на каждом слое (скрытая) | `fail` |

Сверяется командой `./scripts/verify-fixture permission-propagation`.

## Что проверяет скрытая проверка

Одиннадцать сырых ответов API, которых нет в данных проекта (защита от хардкода id и имён):
форматы `ROLE_*`, `role_*`, регистр и пробелы, блокировка у каждой роли, неизвестная роль.
Для каждого права проверяются **на каждом слое**: результат `normalizeUser`, состояние стора,
`store.can` и действия интерфейса. Плюс восемь пользователей проекта через настоящий API и
то, что ответы API не изменены.

Требование «на каждом слое» и отличает причину от симптома:

| Правка | Итог |
| --- | --- |
| `normalizeUser` через `effectivePermissions` (эталон) | pass |
| проверка статуса в `userActions` | fail — стор и `can` по-прежнему неверны |
| пересчёт прав в сторе | fail — `normalizeUser` отдаёт неверного пользователя |
| нормализация роли в API | fail — ответы API изменены, `normalizeUser` на сыром ответе неверен |
| только нормализованная роль, без статуса | fail — заблокированным остаются права |

## Что оценивать вручную

Автоматически не ловится дублирование: модель может переписать карту ролей внутри
`normalizeUser` или добавить свою проверку блокировки вместо `effectivePermissions` — тесты
пройдут. Это `constraint-violation`: промпт прямо запрещает дублировать mapping.

```bash
cp solution/normalizeUser.js fixture/src/auth/normalizeUser.js   # во временной копии
```
