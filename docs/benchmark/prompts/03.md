Тест №3 — Refactor Order Pricing Logic

Название: Refactor order pricing without changing behavior

Краткое описание:
В проекте есть запутанная логика расчёта итоговой цены заказа с несколькими скидками и надбавками. Нужно улучшить структуру кода, сохранив текущее поведение и публичный API.

Тег: refactor

Категория: Refactoring

Сложность: Medium

В проекте находится модуль расчёта стоимости заказа.

Сейчас он работает корректно, но логика расчёта стала трудно читаемой: в одной функции смешаны проверки типа клиента, промокодов, доставки, скидок и дополнительных сборов.

Проведи рефакторинг этого модуля.

Требования:

* не изменяй внешнее поведение расчёта;
* не меняй публичный API модуля;
* не меняй существующие тесты;
* не добавляй новые зависимости;
* сохрани текущий порядок применения скидок, сборов и округления;
* не заменяй существующую реализацию вызовом сторонней библиотеки;
* постарайся разделить ответственность между логическими частями расчёта;
* избегай ненужной абстракции и большого количества мелких сущностей без практической пользы;
* существующие потребители модуля не должны требовать изменений.

После рефакторинга запусти доступные проверки проекта и убедись, что поведение полностью сохранено.

Fixture

pricing/

Но она полностью корректна.

Validation

Здесь baseline отличается от bug/feature тестов:

Original:
existing tests     PASS
hidden tests       PASS

After model:
existing tests     PASS
hidden tests       PASS

Hidden tests должны покрывать комбинации, которых нет в публичных:

VIP + promo;
бесплатная доставка;
express surcharge;
минимальная стоимость заказа;
несколько типов скидок;
граничные значения;
округление денег.

Главная задача validation — поймать ситуацию, когда модель «улучшила» код, но слегка изменила бизнес-логику.

Что оценивать вручную

Здесь одного tests PASS недостаточно.

Human review особенно важен:

PASS, если:

код действительно стал заметно понятнее;
поведение сохранено;
публичный API не изменился;
модель не переусложнила архитектуру.

FAIL, например:

constraint-violation — изменён API;
wrong-solution — поменялось поведение;
incomplete — код практически не улучшен;
отдельная будущая причина вроде over-engineered, если захочется её учитывать.

Этот тест хорошо проверяет качество инженерных решений: слабая модель часто либо почти ничего не меняет, либо превращает одну плохую функцию в десять классов и фабрик.
