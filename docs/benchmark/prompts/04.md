Тест №4 — Add Regression Tests for Cart Rules

Название: Add regression tests for cart rules

Краткое описание:
В проекте есть рабочая логика корзины и описание нескольких бизнес-правил. Нужно добавить тесты, которые действительно защищают эти правила от регрессии.

Тег: tests

Категория: Testing

Сложность: Medium
В проекте находится модуль корзины интернет-магазина.

Текущая реализация работает корректно, но несколько важных бизнес-правил практически не покрыты тестами.

Добавь regression tests для следующих сценариев:

* количество одного товара в корзине не может быть меньше 1;
* количество одного товара не может превышать 10;
* удаление последней единицы товара полностью удаляет позицию из корзины;
* скидка применяется только к товарам, которые участвуют в акции;
* итоговая стоимость корзины не должна становиться отрицательной;
* операции с одним товаром не должны изменять количество других товаров.

Требования:

* не изменяй production-код без необходимости;
* не меняй публичный API;
* не добавляй новые зависимости;
* используй существующий test framework проекта;
* тесты должны проверять наблюдаемое поведение, а не детали внутренней реализации;
* избегай тестов, которые проходят независимо от корректности production-кода;
* не дублируй один и тот же сценарий несколькими почти одинаковыми тестами;
* существующие тесты должны продолжать проходить.

После добавления тестов запусти весь доступный test suite.


Fixture

Например:

cart/
├── src/
│   ├── cart.ts
│   ├── pricing.ts
│   └── types.ts
├── tests/
│   └── basic.test.ts
└── package.json

Production-код изначально корректный, но публичных тестов мало.

Здесь особенно полезна hidden validation не вида «тесты модели проходят», а проверка качества самих тестов.

Можно подготовить несколько скрытых mutant-версий production-кода:

mutation 1:
разрешить quantity = 0

mutation 2:
убрать ограничение max = 10

mutation 3:
применять скидку ко всем товарам

mutation 4:
при удалении менять соседний item

После выполнения модели Arena временно подставляет каждый mutant и запускает написанные моделью тесты.

Хороший результат:

original implementation   PASS

mutation #1              FAIL
mutation #2              FAIL
mutation #3              FAIL
mutation #4              FAIL

То есть тесты реально ловят регрессии.

Это намного сильнее обычной проверки:

npm test → PASS

потому что модель легко может написать пять бессмысленных тестов, которые всегда зелёные.

Для такого типа benchmark я бы даже ввёл отдельную метрику вроде:

Mutations caught: 4 / 4

Но итоговый verdict всё равно оставить обычным PASS / FAIL.
