Тест №2 — Undo / Redo History

Название: Implement undo and redo history

Краткое описание:
В существующий редактор нужно добавить undo/redo для пользовательских изменений состояния, сохранив текущую архитектуру и публичный API.

Тег: feature

Категория: Feature Implementation / State Management

Сложность: Medium
В проекте находится небольшой редактор списка элементов.

Пользователь может:

* добавлять элементы;
* удалять элементы;
* переименовывать элементы;
* менять их порядок.

Добавь поддержку Undo и Redo.

Требования:

* Undo должен отменять последнее пользовательское изменение;
* Redo должен повторно применять отменённое изменение;
* после нового изменения после Undo история Redo должна очищаться;
* история должна хранить не более 20 предыдущих состояний;
* начальная загрузка данных не должна попадать в историю;
* не изменяй существующий публичный API модулей без необходимости;
* не добавляй новые зависимости;
* существующие функции редактора должны продолжать работать;
* не реализуй отдельную историю для каждого типа действия — механизм должен корректно работать с состоянием редактора в целом;
* избегай полного переписывания существующей архитектуры, если задача может быть решена локальным расширением.

После реализации запусти доступные проверки проекта и убедись, что существующее поведение не сломано.

Fixture

Небольшой React + TypeScript проект:

editor/
├── src/
│   ├── App.tsx
│   ├── Editor.tsx
│   ├── editorState.ts
│   └── types.ts
├── tests/
└── package.json

До модели приложение полностью рабочее, просто нет Undo/Redo.

Это хороший fixture, потому что можно нажать Run Original и увидеть полноценный рабочий редактор, а после модели — тот же проект уже с новой возможностью.

Hidden validation

Я бы проверял не только наличие двух кнопок, а последовательности действий.

Например:

Initial:
A, B, C

rename B → X
delete A
move C before X

Undo
→ X, C

Undo
→ A, X, C

Undo
→ A, B, C

Redo
→ A, X, C

И важный edge case:

change A
change B
Undo
new change C
Redo

Redo уже ничего не должен делать.

Ещё скрытые проверки:

после 25 изменений доступны только последние 20;
initial load не отменяется через Undo;
несколько Undo подряд;
несколько Redo подряд;
Undo на пустой истории ничего не ломает;
Redo на пустой истории ничего не ломает;
существующие операции редактора продолжают работать.
Почему этот тест полезен

Здесь почти невозможно просто найти одну неправильную строку и заменить её. Модель должна:

разобраться, где в проекте живёт состояние;
выбрать нормальное место для истории;
не дублировать бизнес-логику;
правильно реализовать переходы past → present → future;
учесть несколько неочевидных edge cases;
понять, когда изменение является пользовательским, а когда нет.

Именно поэтому он хорошо дополняет debugging fixtures: проверяет уже не способность найти дефект, а способность понять чужую архитектуру и аккуратно расширить её.
