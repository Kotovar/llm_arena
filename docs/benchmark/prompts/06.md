Тест №6 — Cross-module Code Understanding

Название: Fix incorrect permission propagation

Краткое описание:
В небольшом приложении права пользователя вычисляются в нескольких слоях. Нужно понять цепочку данных и исправить проблему в правильном месте, не дублируя логику.

Тег: analysis

Категория: Code Understanding / Cross-module Task

Сложность: Hard
В проекте есть система ролей и прав доступа.

Права пользователя проходят через несколько уровней:

* данные пользователя приходят из API;
* роль преобразуется в набор permissions;
* permissions попадают в application state;
* UI использует их для отображения доступных действий.

Сейчас для некоторых пользователей UI показывает неправильный набор доступных действий.

Исправь проблему.

Требования:

* сначала разберись, где именно возникает некорректное состояние;
* исправь причину проблемы, а не её проявление в UI;
* не добавляй дополнительные проверки прав непосредственно в компоненты, если соответствующая логика уже существует в другом слое;
* не дублируй mapping ролей и permissions;
* не меняй публичный API существующих модулей без необходимости;
* не добавляй новые зависимости;
* не хардкодь отдельные user id, роли или permissions ради прохождения конкретного сценария;
* существующее корректное поведение других ролей должно сохраниться;
* не переписывай систему авторизации целиком, если проблема может быть исправлена локально.

После исправления запусти доступные проверки проекта и убедись, что поведение остальных ролей не изменилось.

Fixture

Здесь я бы специально сделал проект чуть более распределённым:

permissions/
├── src/
│   ├── api/
│   │   └── userApi.ts
│   ├── auth/
│   │   ├── rolePermissions.ts
│   │   └── normalizeUser.ts
│   ├── store/
│   │   └── authStore.ts
│   ├── hooks/
│   │   └── usePermissions.ts
│   ├── components/
│   │   └── UserActions.tsx
│   └── types.ts
├── tests/
└── package.json

Баг должен быть не в очевидном месте вроде UserActions.tsx, а, например, в нормализации данных:

const permissions = rolePermissions[user.role] ?? []

при том что API для части пользователей возвращает роль в другом формате или есть дополнительное поле, которое должно учитываться раньше.

Главное — чтобы UI выглядел виноватым, но реальная причина была выше по цепочке.

Hidden validation

Проверять несколько ролей и комбинаций:

Admin
→ create, edit, delete

Editor
→ create, edit

Viewer
→ read only

И один неочевидный сценарий, например:

role: "editor"
status: "suspended"

где итоговые permissions должны быть ограничены.

Хорошая модель должна пройти цепочку данных и исправить место, где формируется каноническое состояние.

Почему этот тест полезен

Он проверяет то, чего почти нет в предыдущих задачах: способность строить ментальную модель проекта.

Слабая модель часто:

чинит UI локальным if;
дублирует permissions mapping;
добавляет исключение для конкретной роли;
исправляет симптом, но оставляет источник некорректных данных.

Сильная модель должна найти слой, где нарушается контракт, и сделать небольшой системный fix.
