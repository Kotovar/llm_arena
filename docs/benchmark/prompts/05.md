Тест №5 — API Integration / Pagination

Название: Implement paginated user loading

Краткое описание:
В существующем приложении нужно подключить постраничную загрузку пользователей через уже предоставленный API-клиент, корректно обработав загрузку, ошибки и повторные запросы.

Тег: api

Категория: API Integration

Сложность: Medium
В проекте есть экран списка пользователей и готовый API-клиент для получения данных.

Сейчас приложение загружает только первую страницу.

Добавь полноценную постраничную загрузку.

Требования:

* первая страница должна загружаться при открытии экрана;
* пользователь должен иметь возможность загрузить следующую страницу;
* новые результаты должны добавляться к уже загруженным, а не заменять их;
* нельзя отправлять запрос следующей страницы, пока предыдущий такой запрос ещё выполняется;
* после получения последней страницы возможность загрузить следующую должна исчезнуть или стать недоступной;
* повторная загрузка одной и той же страницы не должна создавать дубликаты пользователей;
* при ошибке уже загруженные данные должны оставаться на экране;
* после ошибки пользователь должен иметь возможность повторить запрос;
* состояние загрузки первой страницы и загрузки следующей страницы должно корректно различаться;
* используй существующий API-клиент;
* не добавляй новые зависимости;
* не изменяй контракт API;
* не изменяй существующие тесты;
* не хардкодь количество страниц или количество пользователей.

После реализации запусти доступные проверки проекта.

API уже существует:

getUsers({
  page: 1,
})

и возвращает что-то вроде:

{
  users: [...],
  page: 1,
  hasNextPage: true
}

Модель не проектирует API — она должна правильно воспользоваться существующим контрактом.

Hidden validation

Я бы проверял последовательности, которые простой happy-path не ловит.

Например:

page 1
→ [1, 2, 3]

page 2
→ [4, 5, 6]

result
→ [1, 2, 3, 4, 5, 6]

Но дальше интереснее.

Double click
Load more
Load more

пока запрос ещё выполняется.

Ожидание:

GET page=2 → один вызов

а не два.

Ошибка
page 1 → PASS

page 2 → ERROR

На экране всё ещё должны оставаться пользователи первой страницы.

Затем:

Retry
↓
page 2 → PASS

Получаем нормальный объединённый список.

Последняя страница
hasNextPage = false

Новых запросов после этого быть не должно.

Дубликаты

Можно специально вернуть пользователя с тем же id на границе страниц:

page 1 → 1, 2, 3
page 2 → 3, 4, 5

И проверить:

1, 2, 3, 4, 5

если контракт задачи предполагает уникальность по id.

Почему тест полезный

Здесь модель должна одновременно правильно работать с:

чужим API-контрактом;
async состояниями;
React state;
накоплением данных;
concurrency;
error recovery;
edge cases.

При этом это не debugging: исходный проект не сломан. Он просто не реализует необходимое поведение.

Ещё интересно будет смотреть diff моделей. Одна может решить задачу аккуратно небольшим изменением существующего состояния, а другая — построить вокруг простой пагинации половину нового data-layer. Это хорошо проявится в tokens, tool calls, размере diff и будущей метрике over-engineering.
