Тест №1 — Stale Search Results

Название: Fix stale search results

Краткое описание:
В приложении результаты поиска иногда соответствуют предыдущему запросу. Модель должна найти race condition и исправить его, не меняя публичный API и не добавляя зависимости.

Тег: debug

Категория: Debugging

Сложность: Medium

Режим: PI / project workspace

Тело промпта:
В проекте есть поиск пользователей с загрузкой результатов через асинхронный API.

При быстром вводе текста иногда происходит ошибка: пользователь уже ввёл новый запрос, но после завершения более старого запроса интерфейс показывает результаты для предыдущей строки поиска.

Найди причину проблемы и исправь её.

Требования:

* исправь именно причину некорректного поведения;
* не меняй публичный API существующих модулей;
* не добавляй новые зависимости;
* не изменяй существующие тесты;
* не заменяй асинхронный API синхронной заглушкой;
* не добавляй искусственные задержки для обхода проблемы;
* не переписывай компонент или модуль целиком, если проблема может быть исправлена локально;
* существующее корректное поведение приложения должно сохраниться.

После исправления запусти доступные проверки проекта и убедись, что решение работает.

Что должен содержать fixture

Я бы сделал очень маленький React/TypeScript-проект, где логика примерно такая:

useEffect(() => {
  searchUsers(query).then(setUsers)
}, [query])

А searchUsers() специально отвечает с разной задержкой:

"a"   → 300 ms
"ab"  → 50 ms

Последовательность:

query = "a"
↓
request A

query = "ab"
↓
request B

B finishes
→ правильные результаты "ab"

A finishes позже
→ перезаписывает состояние результатами "a"
Validation

Скрытый тест должен воспроизводить именно изменение порядка ответов:

request("a")  ───────────────→ response
request("ab") ───→ response

PASS только если после завершения обоих запросов UI всё ещё показывает результаты "ab".

Дополнительно:

npm test
npm run typecheck
Что здесь интересно измерять

Модель может:

правильно решить race condition → PASS;
добавить debounce, который случайно проходит простой сценарий, но не устраняет race → FAIL / wrong-solution;
поменять API searchUsers → FAIL / constraint-violation;
переписать полпроекта → потенциально PASS по корректности, но это хороший материал для будущих метрик эффективности;
долго исследовать уже исправленный код → проявится Overthinking.

Мне этот тест нравится ещё и потому, что правильное изменение может занимать буквально несколько строк, поэтому количество токенов и tool calls здесь будет хорошо показывать насколько модель умеет быстро локализовать проблему, а не просто способность генерировать много кода.
