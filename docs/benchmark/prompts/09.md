Тест №9 — Booking API

Название: Build a room booking API

Краткое описание:
С нуля создать Node.js API для бронирования переговорных комнат. Нужно реализовать создание и отмену бронирований, проверку пересечений временных интервалов и корректную обработку конкурентных запросов.

Тег: create-backend

Категория: Project Creation / Backend

Сложность: Hard
Создай с нуля HTTP API для бронирования переговорных комнат.

Используй Node.js и TypeScript.

Проект должен запускаться локально стандартной командой из `package.json`.

## Сущность бронирования

Бронирование содержит:

* уникальный `id`;
* `roomId`;
* `title`;
* `start`;
* `end`;
* дату создания.

`start` и `end` передаются как ISO 8601 date-time строки.

## API

Реализуй следующие операции.

### Создать бронирование

`POST /bookings`

Пример тела:

```json
{
  "roomId": "room-1",
  "title": "Planning",
  "start": "2026-10-01T10:00:00Z",
  "end": "2026-10-01T11:00:00Z"
}
```

При успешном создании верни созданное бронирование.

### Получить бронирование

`GET /bookings/:id`

### Получить список бронирований комнаты

`GET /rooms/:roomId/bookings`

Результат должен быть отсортирован по времени начала.

### Отменить бронирование

`DELETE /bookings/:id`

---

## Главное бизнес-правило

В одной комнате не может существовать два пересекающихся бронирования.

Например:

```text
10:00 ───── 11:00
       10:30 ───── 11:30
```

такое бронирование должно быть отклонено.

Но соседние интервалы допустимы:

```text
10:00 ───── 11:00
               11:00 ───── 12:00
```

То есть окончание одного бронирования может совпадать с началом следующего.

Бронирования разных комнат друг другу не мешают.

---

## Валидация

API должен отклонять некорректные данные, включая:

* отсутствующий `roomId`;
* пустой `title`;
* некорректные даты;
* `start >= end`;
* некорректный JSON.

Используй подходящие HTTP status codes и возвращай понятный JSON с ошибкой.

---

## Конкурентные запросы

Корректность проверки пересечений должна сохраняться, даже если два конфликтующих запроса на создание бронирования приходят почти одновременно.

Не должно быть состояния, при котором оба конфликтующих бронирования успешно создаются только потому, что оба запроса проверили доступность до записи результата.

---

## Хранение данных

Внешняя база данных не требуется.

Допустимо использовать:

* память процесса;
* либо простое локальное файловое хранилище.

Выбери подходящий вариант для небольшой задачи.

Не используй внешние сервисы.

---

## Требования

* Node.js;
* TypeScript;
* понятная структура проекта;
* проект должен запускаться одной стандартной командой;
* добавь production/start command;
* добавь команду для проверки типов или сборки;
* не хардкодь конкретные комнаты или даты;
* не хардкодь ответы под примеры из задания;
* бизнес-логика проверки пересечений не должна зависеть от HTTP слоя;
* корректно обрабатывай неизвестные booking id;
* не допускай необработанных исключений, приводящих к падению процесса;
* не добавляй frontend;
* не добавляй внешнюю базу данных.

После реализации запусти доступные проверки и самостоятельно проверь основные сценарии работы API.
Почему задача хорошая

На первый взгляд это обычный backend CRUD, но скрытые проверки могут довольно хорошо разделить модели.

Базовая validation:

project installs       PASS
typecheck/build        PASS
server starts          PASS

Далее HTTP:

POST booking           201
GET booking            200
GET room bookings      200
DELETE booking         204/200
GET missing booking    404

Но основная часть — интервалы.

Например:

existing:
10:00 — 11:00

Проверяем:

09:00 — 10:00   PASS
11:00 — 12:00   PASS

09:30 — 10:30   FAIL
10:30 — 11:30   FAIL
10:15 — 10:45   FAIL
09:00 — 12:00   FAIL
10:00 — 11:00   FAIL

И отдельно:

room-1: 10:00 — 11:00
room-2: 10:00 — 11:00

PASS
Самая интересная hidden-проверка — concurrency

Отправить почти одновременно:

request A:
room-1
10:00 — 11:00

request B:
room-1
10:30 — 11:30

В итоге должно быть:

один SUCCESS
один CONFLICT

а в хранилище — ровно одно бронирование.

Это уже проверяет, понимает ли модель отличие:

if (!hasOverlap()) {
  await something()
  save()
}

от атомарной операции.

Ещё полезный edge case

После:

10:00 — 11:00
DELETE

тот же временной слот снова должен стать доступным.

Такой backend-тест хорошо дополняет Kanban: там модель сама строит frontend-проект, а здесь уже проверяется HTTP, разделение слоёв, бизнес-логика, validation, error handling и немного concurrency reasoning.
