Тест №8 — Create a Mini Kanban Board

Название: Build a mini Kanban board

Краткое описание:
С нуля создать небольшое React + TypeScript приложение с тремя колонками, карточками задач, drag-and-drop без сторонней DnD-библиотеки и сохранением состояния.

Тег: create

Категория: Project Creation / Frontend

Сложность: Hard
Создай с нуля небольшое приложение Kanban Board.

Используй React и TypeScript.

Приложение должно запускаться локально стандартной командой из `package.json`.

## Функциональность

На доске должны быть три колонки:

* Todo
* In Progress
* Done

Пользователь должен иметь возможность:

* создать новую задачу;
* указать название задачи;
* перемещать задачу между колонками;
* менять порядок задач внутри одной колонки;
* переименовывать задачу;
* удалять задачу.

Перемещение карточек должно работать через drag-and-drop.

Не используй стороннюю drag-and-drop библиотеку.

## Состояние

Состояние доски должно сохраняться между перезагрузками страницы.

При первом запуске покажи несколько демонстрационных задач.

После того как пользователь изменил доску, перезагрузка страницы не должна восстанавливать демонстрационные данные поверх пользовательских.

## Требования

* используй React;
* используй TypeScript;
* не используй backend;
* не добавляй UI framework;
* не используй стороннюю drag-and-drop библиотеку;
* приложение не должно зависеть от внешнего API;
* добавь понятный `package.json`;
* проект должен запускаться одной стандартной командой;
* не хардкодь поведение только для демонстрационных карточек;
* карточки должны иметь устойчивые уникальные идентификаторы;
* приложение должно корректно работать и с пустой колонкой;
* пользователь не должен иметь возможность создать задачу с пустым названием.

Интерфейс должен быть аккуратным и пригодным для обычного использования, но основное внимание удели корректности поведения, структуре проекта и завершённости реализации.

После реализации запусти доступные проверки и убедись, что проект собирается и запускается.
Здесь fixture почти отсутствует. Arena создаёт чистый workspace, например:

workspace/
└── README.md   // возможно вообще ничего

И модель должна сама создать:

package.json
src/
...

Это уже хорошо проверяет совсем другие свойства модели:

умеет ли начать проект с нуля;
выбирает ли нормальную структуру;
создаёт ли действительно запускаемый результат;
помнит ли все требования из длинного prompt;
доводит ли работу до конца;
проверяет ли собственный проект;
не начинает ли бесконечно полировать уже работающий результат.
Что можно проверить автоматически

Здесь validation особенно интересна.

Сначала базовая инфраструктура:

install dependencies       PASS
typecheck                  PASS
build                      PASS
application starts         PASS

А затем hidden browser/e2e tests:

create task
→ карточка появилась

reload
→ карточка сохранилась

rename
→ новое название отображается

reload
→ новое название сохранилось

delete
→ карточка исчезла

drag Todo → Done
→ карточка находится в Done

reload
→ всё ещё находится в Done

Отдельно:

empty title
→ задача не создаётся

и:

перемещение в пустую колонку
→ работает
Проверка ограничения по DnD

Можно автоматически проверить зависимости:

package.json

и запрещённый список вроде:

@dnd-kit/*
react-beautiful-dnd
react-dnd

Но не надо требовать конкретную реализацию. Модель может использовать HTML5 Drag and Drop API, pointer events и т.п.

Почему именно такой creation-тест

Он заметно отличается от предыдущих.

В bug/refactor-задачах модели уже дают архитектуру и большую часть решений. Здесь ей самой приходится принимать десятки мелких инженерных решений.

При этом результат всё ещё достаточно объективно проверяем.

Это лучше для benchmark, чем что-нибудь вроде:

Сделай красивый лендинг.

У лендинга слишком много субъективной оценки.

У Kanban можно получить довольно жёсткий итог:

Build                    PASS
Starts                   PASS
Create                   PASS
Rename                   PASS
Delete                   PASS
Move between columns     PASS
Reorder                  PASS
Persistence              PASS
Constraints              PASS

Human verdict            PASS

И здесь особенно интересными будут total time, generated tokens, tool calls, размер проекта и Overthinking после первого успешного build/e2e.
