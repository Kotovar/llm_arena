Тест №7 — Dependency Resolver

Название: Implement dependency resolution order

Краткое описание:
Нужно реализовать вычисление корректного порядка выполнения задач с зависимостями, включая обработку отсутствующих зависимостей и циклов.

Тег: algorithm

Категория: Algorithm / Reasoning

Сложность: Medium
В проекте есть модуль планирования задач.

Каждая задача имеет уникальный `id` и может зависеть от других задач.

Реализуй функцию, которая возвращает порядок выполнения задач так, чтобы каждая задача выполнялась только после всех своих зависимостей.

Требования:

* каждая задача должна присутствовать в результате ровно один раз;
* все зависимости задачи должны находиться в результате раньше самой задачи;
* задачи без зависимостей могут выполняться сразу;
* порядок независимых задач должен быть детерминированным;
* если задача ссылается на несуществующую зависимость, функция должна вернуть предусмотренную проектом ошибку;
* если в графе зависимостей есть цикл, функция должна вернуть предусмотренную проектом ошибку;
* self-dependency также считается циклом;
* входные данные нельзя изменять;
* не добавляй новые зависимости;
* не меняй публичный API существующего модуля;
* не хардкодь решения под конкретные входные данные;
* решение должно корректно работать с произвольным количеством задач в рамках существующего API.

После реализации запусти доступные проверки проекта.

Fixture

Очень небольшой TypeScript-проект:

dependency-resolver/
├── src/
│   ├── resolveOrder.ts
│   ├── errors.ts
│   └── types.ts
├── tests/
│   └── basic.test.ts
└── package.json

Например API уже задан:

type Task = {
  id: string
  dependencies: string[]
}

export function resolveOrder(tasks: readonly Task[]): string[]

Ошибки тоже лучше заранее определить в fixture, чтобы модель не придумывала собственный контракт.

Public tests

Только базовые случаи:

A
B depends on A

→ A, B

и несколько независимых задач.

Hidden validation

Основная ценность теста именно здесь.

Проверки:

A → B → C
A depends on B
A depends on C
B depends on D

несколько disconnected-графов;

diamond dependency:

    A
   / \
  B   C
   \ /
    D

отсутствующая dependency;

простой цикл:

A → B → A

длинный цикл:

A → B → C → D → B

self-cycle:

A → A

дублирующиеся dependency entries;

пустой список;

большой граф.

Важный момент — детерминированность

Например fixture может определять правило:

если одновременно доступны несколько задач, использовать порядок их появления во входном массиве.

Тогда hidden validator способен проверять не только валидный topological sort, но и конкретный стабильный результат.

Иначе у задачи может быть много правильных ответов:

A, B, C

и

B, A, C

оба корректны.

Для автоматического benchmark это лишняя неоднозначность.

Почему этот тест полезен

Здесь практически нет UI, архитектуры React или поиска по проекту. Модель должна:

распознать задачу как работу с directed graph;
выбрать корректный алгоритм;
обработать cycle detection;
не забыть missing dependencies;
сохранить deterministic ordering;
не мутировать input;
пройти неизвестные заранее edge cases.

Такой тест хорошо выявит модель, которая выглядит сильной на генерации приложений, но начинает ошибаться на компактной задаче, где корректность определяется достаточно строго.
