Тест №11 — Transactional Wallet Service

Здесь я бы добавил задачу на БД, транзакции и целостность данных. Это будет сильно отличаться и от CRUD API, и от алгоритмических задач.

Название: Build a transactional wallet service

Краткое описание:
Создать Node.js сервис переводов между кошельками с SQLite. Главная проверка — корректность транзакций, конкурентных переводов и сохранение денежных инвариантов.

Тег: database

Категория: Backend / Database / Concurrency

Сложность: Hard
Создай небольшой backend-сервис на Node.js и TypeScript для управления кошельками и переводами денег между ними.

Для хранения данных используй SQLite.

Проект должен запускаться локально стандартной командой из `package.json`.

## Кошелёк

Каждый кошелёк содержит:

* уникальный `id`;
* `balance`;
* дату создания.

Денежные значения должны храниться способом, который не приводит к ошибкам вычислений с floating point.

## API

Реализуй следующие операции.

### Создать кошелёк

`POST /wallets`

Пример:

```json
{
  "initialBalance": 10000
}
```

`initialBalance` задаётся в минимальных денежных единицах, например в центах.

### Получить кошелёк

`GET /wallets/:id`

### Выполнить перевод

`POST /transfers`

Пример:

```json
{
  "fromWalletId": "wallet-1",
  "toWalletId": "wallet-2",
  "amount": 2500
}
```

### Получить историю переводов

`GET /wallets/:id/transfers`

История должна содержать как входящие, так и исходящие переводы и быть отсортирована по времени создания.

## Правила перевода

Перевод должен быть выполнен только целиком.

Нельзя допускать состояние, при котором деньги уже списаны с одного кошелька, но ещё не зачислены на другой.

Перевод должен быть отклонён, если:

* исходный кошелёк не существует;
* целевой кошелёк не существует;
* сумма меньше или равна нулю;
* кошелёк переводит деньги сам себе;
* на исходном кошельке недостаточно средств.

Баланс кошелька никогда не должен становиться отрицательным.

## Конкурентные переводы

Сервис должен сохранять корректность при одновременных запросах.

Например, если на кошельке находится `10000`, а одновременно приходят два перевода:

```text
7000
7000
```

не должно быть возможным, чтобы оба перевода успешно завершились.

После обработки всех запросов баланс не должен нарушать бизнес-правила.

## История переводов

Успешный перевод должен создавать ровно одну запись истории.

Неуспешный перевод не должен создавать частичную или ошибочную запись.

Каждая запись должна содержать минимум:

* уникальный id;
* исходный кошелёк;
* целевой кошелёк;
* сумму;
* дату создания.

## Надёжность

Если выполнение перевода завершается ошибкой после начала операции, состояние базы данных должно оставаться согласованным.

Используй возможности базы данных для обеспечения атомарности там, где это необходимо.

## Требования

* Node.js;
* TypeScript;
* SQLite;
* не использовать внешние сервисы;
* не использовать floating point для хранения денежных значений;
* не хранить состояние кошельков только в памяти;
* бизнес-логику переводов отдели от HTTP-обвязки;
* не хардкодь идентификаторы или суммы из примеров;
* используй подходящие HTTP status codes;
* ошибки API должны возвращаться в предсказуемом JSON-формате;
* приложение не должно падать из-за некорректного пользовательского ввода;
* добавь команды запуска и проверки проекта.

После реализации проверь обычные и конкурентные сценарии перевода и убедись, что состояние базы данных остаётся корректным.
Что проверять hidden validation

Самый важный инвариант:

общая сумма денег до операций
=
общая сумма денег после операций

если никакого создания/удаления денег API не предоставляет.

Например:

A = 10 000
B = 5 000
C = 2 000

Total = 17 000

После десятков успешных и неуспешных переводов:

Total = 17 000

Также проверять обычный перевод:

A = 10 000
B = 5 000

A → B: 2 500

A = 7 500
B = 7 500

недостаток средств:

A = 1000

transfer 1500
→ FAIL

balance = 1000
history unchanged

и особенно concurrency:

A = 10 000

parallel:
A → B: 7 000
A → C: 7 000

Ожидание:

ровно один перевод успешен
ровно один отклонён
A >= 0

Ещё сильнее тест:

A = 100 000

100 конкурентных переводов по 1 500

После завершения:

ни один кошелёк не ушёл в минус;
количество history records совпадает с числом успешных переводов;
деньги не появились и не исчезли.
Почему тест полезный

Он проверяет вещи, которые почти не затрагивали предыдущие задачи:

SQL;
schema design;
persistence;
транзакции;
atomicity;
concurrency;
денежные значения;
инварианты данных.

Причём слабое решение может выглядеть совершенно рабочим при обычном ручном тестировании:

const wallet = await getWallet(id)

if (wallet.balance >= amount) {
  await updateBalance(...)
}

и провалиться только при конкурентных запросах.

Для benchmark это хороший тип задачи: happy path простой, а настоящая корректность обнаруживается hidden tests.
