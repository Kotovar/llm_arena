# Как написать benchmark-fixture

Инструкция для автора — человека или агента. Fixture — это каталог `fixtures/<id>/`; движок
арены правок не требует, каталог с `benchmark.json` подхватывается при старте сервера.

Образцы по типам задач:

| Тип | Fixture | Приём скрытой проверки |
| --- | --- | --- |
| Правка бага | `stale-search-results` | регрессионный тест на сценарий бага |
| Фича | `list-editor-history`, `debounce-utility`, `todo-filters` | тесты на заданный контракт |
| Алгоритм | `dependency-resolver` | свойства результата, а не конкретная строка |
| Рефакторинг | `order-pricing-refactor` | оракул: сравнение с замороженной копией исходника |
| Написание тестов | `cart-regression-tests` | мутанты: тесты модели должны их поймать |
| Интеграция с API | `users-pagination` | управляемый клиент, проверка последовательностей |
| Понимание кода | `permission-propagation` | верное состояние на каждом слое, а не только в UI |

Прежде чем писать свой, откройте ближайший по типу и его `README.md`.

## Каталог

```text
fixtures/<id>/
├── benchmark.json   манифест
├── README.md        для людей: что за задача, состояние, что проверяет скрытая проверка
├── fixture/         исходный проект — ровно то, что получит модель
├── validation/      скрытая проверка — копируется поверх результата, модель её не видит
└── solution/        эталонное решение — модель его не видит, движок его не использует
```

`validation/` копируется в **корень** workspace с сохранением подкаталогов, поэтому импорты в
скрытых тестах пишутся от корня проекта: `./src/...`, а не `../src/...`.

## Язык и зависимости

- **Никаких зависимостей.** Ни `node_modules`, ни `install`: прогон не ходит в сеть, и ревизия
  дерева полностью описывает условия. Тесты — `node:test` и `node:assert/strict`.
- **Приложения — чистые ES-модули (`.js`).** Их одинаково исполняют браузер и Node, сборки нет.
  Промпт про React переводится на голый DOM: суть задачи (гонка, состояние, догрузка) от этого
  не меняется. Представление держите тонким, а логику — в модуле, который тестируется в Node
  без DOM (контроллер, стор).
- **Логика — можно TypeScript.** Node 24 исполняет `.ts` сам, срезая типы: `enum`,
  `namespace` и parameter properties не работают. Скажите это модели в `instructions`.
- **Превью** — `server.mjs` из любого фронтового fixture, копия без изменений. Для `.ts` в
  браузере — вариант из `dependency-resolver` (`stripTypeScriptTypes`).

## benchmark.json

```json
{
  "id": "<id>",                  // совпадает с именем каталога
  "name": "Implement ...",       // английское название, как в промпте
  "instructions": "...",         // на английском, дописывается к заданию: как запускать, что не трогать
  "reproduction": "...",         // на русском, для ревьюера: как увидеть разницу и на что смотреть
  "checks": [...],               // видимые проверки — модель может их запускать
  "hidden": [...],               // скрытые проверки
  "baseline": { "<check id>": "pass" | "fail" },
  "limits": { "maxDurationMs": 600000 },
  "preview": { "command": { "argv": ["node", "server.mjs"], "timeoutMs": 120000 }, "readyPath": "/" }
}
```

Проверка — `{ "id", "label", "command": { "argv", "timeoutMs"? } }`, id уникальны по обоим
спискам. `preview` — только если есть что открыть в браузере; задачи про одну функцию
судятся по патчу. Лимит — 5 минут для маленькой задачи, 10 для средней, 15 для сложной.

**Скрытый тест запускайте по имени файла**, а не по каталогу: `["node", "--test",
"my-check.test.js"]`. Видимая проверка `node --test` без аргументов найдёт только тесты
проекта — скрытых в workspace модели нет.

## Скрытая проверка

Главный вопрос: **отличает ли она настоящее решение от обхода и от почти правильного**.

1. **Воспроизводит ровно заданное поведение.** Не «тесты проходят», а сценарий из промпта:
   старый ответ приходит позже нового, двойной клик, пользователь на границе страниц.
2. **Не зависит от конкретного решения.** Проверяйте наблюдаемое поведение через публичный
   контракт fixture. Если контракт нужно назвать (имена методов), назовите его в тексте
   задачи, как в `todo-filters`.
3. **Не опирается на данные проекта.** Добавьте входы, которых в `fixture/` нет, — иначе
   проходит хардкод id и имён (`permission-propagation`).
4. **Не виснет.** Не ждите промисы решения: неразрешённый промис даст таймаут вместо честного
   падения. Управляемые промисы + `setImmediate`, или `t.mock.timers`, или стенные часы с
   запасом (`stale-search-results`).
5. **Проверена на мутантах эталона.** Возьмите `solution/`, внесите правдоподобную ошибку —
   ту, которую сделала бы слабая модель, — и убедитесь, что скрытая проверка падает. Три–восемь
   мутантов, список — в README fixture.

Особые приёмы:

- **Рефакторинг** — `baseline` скрытой проверки `pass`. Оракул — копия исходной функции в
  `validation/` со своими типами, сравнение на тысячах сгенерированных входов с
  детерминированным генератором. Деньги — в целых центах, иначе равнозначный рефакторинг
  разойдётся на плавающей точке.
- **Написание тестов** — скрытая проверка — скрипт, который запускает тесты модели на исходнике
  из `validation/original-src/` (не из `src/` — иначе модель подгонит код под тесты) и на
  каждом мутанте. **`original-src/` — копия `fixture/src/`, при правке обновлять обе.**
- **Причина выше симптома** — проверяйте состояние на каждом слое, тогда правка симптома в UI
  проваливается.

## Чек-лист

- [ ] Исходный проект работает: видимые тесты проходят, превью открывается.
- [ ] Баг воспроизводится или фичи нет — ровно так, как описано в промпте.
- [ ] Причина не помечена `TODO`, `FIXME` или комментарием «здесь баг». Заглушка фичи может
      быть названа заглушкой.
- [ ] Неродственная функциональность цела и покрыта видимыми тестами.
- [ ] Эталон проходит все проверки, включая видимые.
- [ ] Скрытая проверка падает на мутантах эталона.
- [ ] Ни один файл `validation/` не лежит в `fixture/`.
- [ ] `README.md` описывает состояние, скрытую проверку, мутантов и что оценивать вручную.
- [ ] `./scripts/verify-fixture <id>` пишет `Fixture is in the declared state.`

Проверить эталон и мутанта во временной копии:

```bash
tmp=$(mktemp -d)
cp -r fixtures/<id>/fixture/. "$tmp" && cp -r fixtures/<id>/validation/. "$tmp"
cp fixtures/<id>/solution/<file> "$tmp/src/"          # эталон или испорченная копия эталона
(cd "$tmp" && node --test && node --test <hidden>.test.js)
```

`verify-fixture` эталон не прогоняет — только исходное состояние против `baseline`.

## Подключение к арене

1. **Перезапустить сервер** — fixtures читаются при старте. Под `pnpm dev` достаточно
   `touch apps/server/src/main.ts`, но сначала убедиться, что нет активных прогонов
   (`GET /api/runs`, статусы `pending`, `running`): перезапуск их оборвёт.
2. **Создать задачу**: `POST /api/tasks` с
   `{ kind: "coding", fixtureId, name, description, prompt, tags }`. Промпт — на русском, в стиле
   существующих: контекст, что сделать, список требований, «запусти доступные проверки».
   Теги — `benchmark`, `cat:<категория>`, `diff:easy|medium|hard`.
3. **Собрать ревизию состава**: `POST /api/suites/<id>/revisions` с `{ taskIds }` — полным
   списком задач, не только новой. Прогоны по старой ревизии с новыми не сравниваются, поэтому
   несколько fixtures разумно добавлять одной ревизией.
