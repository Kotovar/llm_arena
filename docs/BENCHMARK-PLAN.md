# Benchmark Mode — план реализации

Систематический прогон одной модели по фиксированному набору задач: `solved / total`.
Документ — и проект архитектуры, и рабочий чек-лист: каждая фаза закрывается отдельно.

Исходные материалы: [техническое задание](benchmark/spec.md) и
[шестнадцать черновых промптов](benchmark/prompts/README.md).

## 0. Принятые решения

Согласовано до начала работы; менять — только явным решением, не по ходу реализации.

| Вопрос | Решение | Следствие |
| --- | --- | --- |
| Зависимости fixtures | Только без зависимостей: `node:test`, `node:assert`, голый TypeScript и DOM | В репозитории нет вендоренных пакетов, прогон не ходит в сеть, ревизия fixture полностью описывает условия. React-задачи переписываются на голый DOM |
| Состав первого suite | `Coding General v1` — только задачи с исходным проектом (промпты 1–7, 12, 13) | Прогон около часа, задачи сравнимы между собой. Задания «создай с нуля» — отдельный suite после MVP |
| Категория и сложность | Теги с префиксом `cat:` и `diff:` | Ноль изменений схемы, редактор тегов и фильтры уже есть |
| Сколько бенчмарков | Один. Ротация промптов — новой ревизией состава, а не новым бенчмарком (решение 2026-09-17) | UI не создаёт и не архивирует наборы; API `/api/suites` остаётся, но экран берёт первый набор. `Build From Scratch v1` после MVP потребует пересмотреть это решение |
| Leaderboard и Analytics | Бенчмарк живёт на своих страницах | Существующие экраны с оценкой 1–10 не трогаем: бинарный вердикт и балл смешивать в одной цифре нечестно |

## 1. Ответ на главный вопрос

**Насколько Arena уже умеет `broken fixture → model workspace → validation → before/after →
human verdict`?**

Умеет целиком, кроме трёх вещей. Этот путь — не новый режим, а то, что сегодня делает
обычный прогон задачи с `kind: "coding"`.

| Шаг задания | Что уже есть | Файл |
| --- | --- | --- |
| immutable fixture | `fixtures[]` в конфиге, `fixtureManifestSchema` с `install` / `checks` / `preview` | `apps/server/src/config.ts`, `packages/shared/src/index.ts` |
| run workspace | `prepareWorkspace()`: `cp -a --reflink=auto`, `git init`, baseline-коммит | `apps/server/src/artifacts.ts` |
| исполнение | `pi` раннер на четырёх инструментах, флаги чистоты `PI_CLEAN_FLAGS` | `apps/server/src/runners/commands.ts` |
| public validation | `#runChecks()` гоняет `fixture.checks` в workspace | `apps/server/src/engine.ts` |
| result snapshot | `finalizeWorkspace()`: коммит результата, `diff.patch`, список файлов | `apps/server/src/artifacts.ts` |
| before/after | `PreviewManager` поднимает любую версию по `resultSha` и держит два превью | `apps/server/src/preview.ts` |
| diff / файлы / логи | `/api/task-runs/:id/{diff,files,logs,preview-image}` | `apps/server/src/app.ts` |
| human verdict | `reviews`, `completion`, `broken_at`, `classifyTaskRun()` | `packages/shared/src/outcome.ts` |
| model snapshot | `snapshot_json` прогона и задачи: модель, профиль, GPU, версии `pi` и `llama-server`, `ggufSha256` | `apps/server/src/engine.ts:#environment` |
| watchdog | `createWatchdog()` → `AgentLoopError` → статус `agent_loop` → исход `watchdog` | `apps/server/src/watchdog.ts` |
| telemetry | `normalizedMetricsSchema`: TTFT, токены, tok/s, контекст, запросы к модели | `packages/shared/src/index.ts` |
| последовательность и восстановление | один воркер `#pump()`, пропуск уже выполненных позиций, `recoverInterruptedRuns()` | `apps/server/src/engine.ts`, `store.ts` |

Не хватает ровно трёх вещей, и они же — суть всей работы:

1. **Suite с версией.** Сейчас список задач прогона (`run_tasks`) собирается на лету в UI.
   Сравнивать два прогона «по одному и тому же набору» нечем.
2. **Hidden validation.** Все проверки лежат внутри workspace, модель их читает и может
   писать решение прямо под ассерты.
3. **Бинарный вердикт + причина.** Сегодня оценка — четыре балла от 1 до 10; для
   `solved / total` нужен `pass` / `fail` с причиной.

Плюс два мелких пробела: у задачи нет своего лимита времени (`taskTimeoutMs` — это пауза без
вывода, а не общий лимит), и нет проверки, что исходный fixture действительно в нужном
состоянии.

Вывод: **новый движок не нужен.** Нужны три небольшие надстройки и набор fixtures.

### Найденный мусор

Два слота заведены и не заполняются — в них и поедет новая семантика:

- `task_revisions.fixture_hash` всегда `null` (`store.ts:548`);
- таблица `check_runs` создаётся, но пишется только `DELETE` — проверки живут в `result_json`.

## 2. Что переиспользуем без изменений

Модели, профили, калибровка, очередь, `ProcessSupervisor`, редактор задач и тегов, gallery,
compare, analytics, батчи, экспорт/импорт задач, `PreviewManager`, скриншоты, GPU-сэмплер и
термозащита, `describeGenerationError`, повтор при сорванном tool call.

**Benchmark Test — это ревизия задачи.** `task_revisions` уже неизменяемы, уже несут
`content_hash`, `fixture_id`, теги и промпт. Отдельной сущности `BenchmarkTest` не будет.

**Model / Environment Snapshot уже пишутся.** `snapshot_json` задачи содержит модель, профиль,
runner и fixture; `snapshot_json` прогона — ещё и окружение с версиями. Добавляем в него только
ревизию fixture и версию benchmark-окружения.

## 3. Что добавляем

Пять вещей. Ничего больше.

### 3.1 Fixture как каталог репозитория

Сейчас fixture объявляется строкой в `arena.config.yaml`. Для сценария «агент добавляет новый
fixture» это неудобно: локальный конфиг смешивается с содержимым репозитория.

```text
fixtures/
  stale-search-results/
    benchmark.json        # тот же fixtureManifestSchema + новые поля
    fixture/              # ровно это копируется в workspace модели
    validation/           # скрытые проверки, в workspace не попадают
    solution/             # опциональное эталонное решение, только для разработчика
    README.md
```

`loadConfig()` сканирует `fixtures/*/benchmark.json` и добавляет найденное к списку из YAML.
`source` по умолчанию — `./fixture`. Существующие `web-app` и `node-smoke` продолжают
работать из YAML, переписывать их не нужно.

Новые поля манифеста:

```ts
hidden: Check[]            // проверки, которых модель не видит
baseline: Record<string, "pass" | "fail">   // ожидаемое состояние исходного fixture
limits?: { maxDurationMs?: number }
```

`Check` — уже существующий `{ id, label, command }`.

### 3.2 Ревизия fixture — бесплатно

`prepareWorkspace()` уже делает `git init` + коммит. Добавляем одну строку:
`git rev-parse HEAD^{tree}`. Дерево — чистый хеш содержимого, стабильный между запусками
(в отличие от sha коммита с его временем). Это и есть `FixtureRevision`.

Хеш пишется в мёртвую колонку `task_revisions.fixture_hash` и в снапшот задачи. Правка
fixture после прогонов их историю не меняет; в сравнении видно, что ревизии разные.

### 3.3 Hidden validation

`prepareWorkspace()` копирует только `${source}/.`, то есть подкаталог `fixture/`. Каталог
`validation/` физически не попадает в workspace — модель его не видит и не может прочитать.

После работы модели:

```text
finalizeWorkspace()              → resultSha
materializeWorkspaceVersion()    → .data/runs/<run>/<task>/hidden/  (одноразовая копия)
cp validation/ → hidden/
#runChecks(manifest.hidden)      → результаты
rm -rf hidden/
```

Скрытые проверки гоняются в отдельной копии, поэтому в `diff.patch` и в превью результата их
файлов нет. Реализация — та же функция `#runChecks()`, второй вызов с другим списком.

### 3.4 Baseline Verification

Одна функция `verifyFixture(manifest)`: разворачивает workspace из fixture, гоняет `install`,
public и hidden проверки, сравнивает с объявленным `baseline`.

Универсального правила «исходный fixture обязан падать» нет — состояние объявляется в
манифесте, поэтому одинаково поддерживаются bug fix (`regression: "fail"`), feature
(`feature-tests: "fail"`, `existing-tests: "pass"`), refactoring и testing-задачи (всё `pass`).

Вызывается из двух мест: `POST /api/fixtures/:id/verify` и `scripts/verify-fixture` — одна и
та же функция, чтобы агент мог проверить свою работу без запуска UI.

### 3.5 Suite, вердикт, лимит времени

Три маленькие вещи в базе:

```sql
CREATE TABLE suites (id, name, archived_at, created_at, updated_at);
CREATE TABLE suite_revisions (id, suite_id, revision, items_json, content_hash, created_at,
                              UNIQUE(suite_id, revision));
-- items_json: [{ taskRevisionId, fixtureHash }] в фиксированном порядке
ALTER TABLE benchmark_runs ADD COLUMN suite_revision_id TEXT;
CREATE TABLE task_verdicts (task_run_id PRIMARY KEY, verdict, reason, comment, updated_at);
```

`content_hash` ревизии suite считается по списку `taskRevisionId + fixtureHash`. Совместимость
двух прогонов = одинаковый `suite_revision_id` + одинаковый `benchmarkEnvironmentVersion` в
снапшоте. Всё остальное сравнение UI помечает как исследовательское.

Лимит времени: у `#taskControllers` уже есть `cancelTask(taskRunId)`. Таймер на
`limits.maxDurationMs` дёргает его же. Нужен новый `StopReason` — `"timeout"` — и новая ветка в
`classifyTaskRun()`.

## 4. Категории и сложность — через теги

У задач уже есть свободные теги с готовым UI и фильтрами. Категория и сложность едут
зарезервированными префиксами: `cat:debugging`, `diff:hard`.

```text
# ponytail: категория и сложность — теги с префиксом, не колонки.
# Потолок: опечатку в теге ничто не ловит. Отдельные колонки — когда список категорий
# застынет и понадобится валидация на входе.
```

Ноль изменений схемы, ноль работы в редакторе задач, новые категории добавляются сами (§9
задания). Аналитика по категориям читает префикс.

## 5. Модель исполнения

Canonical environment первой версии: **PI Benchmark v1** — раннер `pi-local` с
`PI_CLEAN_FLAGS` и четырьмя встроенными инструментами. Второго механизма инструментов не
появляется; версия окружения — строка в снапшоте прогона.

OMP-прогоны сохраняются теми же таблицами, но с другим `harness` в снапшоте, и в сравнении
помечаются как несовместимые. Full Agent Benchmark — после MVP.

### Жизненный цикл прогона

Переиспользуем существующий `RunStatus` (`pending / running / completed / failed / cancelled /
agent_loop`). Новое состояние `awaiting-review` не заводим: прогон завершён, а наличие
непроставленных вердиктов выводится из `task_verdicts` — это ноль невозможных состояний вместо
ещё одного enum.

Ревью делается после всего прогона, чтобы человек не блокировал многочасовой run. Это уже так
и работает: оценки ставятся на странице результатов.

### Жизненный цикл задачи

Исход по-прежнему считает `classifyTaskRun()` — единственное место сведения статуса, отметок
человека и причины остановки. Добавляем в него `timeout`.

| Исход | Откуда | Вердикт |
| --- | --- | --- |
| `full` / `partial` / `completed` | агент дошёл до конца, проверки прошли | ждёт человека |
| `check_failed` | public или hidden проверка упала | авто `fail`, причина `tests-failed` |
| `watchdog` | зациклился | авто `fail`, причина `watchdog-kill` |
| `timeout` | лимит задачи | авто `fail`, причина `timeout` |
| `error` | раннер упал | авто `fail`, причина `agent-crash` |
| `post_processing` | упал служебный шаг арены | вне процентов, не вина модели |
| `aborted_user` | человек остановил | вне процентов |

Автоматические причины проставляются сразу; человек их видит и может переопределить. Ручной
вердикт нужен только там, где техника молчит: `wrong-solution`, `incomplete`,
`constraint-violation`.

**Одна попытка.** Повтор задачи заводит обычный прогон вне suite и benchmark-результат не
меняет. Существующий `retry` для suite-прогонов отключается.

## 7.1 Чему научил первый прогон

Первый прогон на локальной модели измерил не то, что задумано, и разобрать почему оказалось
важнее самого результата.

**Движок игнорировал исходный проект задачи.** Режим результата переопределял вид задачи
всегда, поэтому «text» превращал кодовую задачу в обычный промпт без проекта. Модель получала
пустой каталог и задание про проект, которого нет. Проверок при этом не запускалось вовсе:
без fixture их просто нет.

**Модель нашла ответы в репозитории.** Оставшись без проекта, она пошла искать его по файловой
системе и нашла — вместе со скрытыми проверками и эталонным решением, и скопировала всё к
себе. По логам: 22, 122 и 26 обращений к этим путям в трёх задачах. Это ровно тот риск,
который в фазе 3 был отложен с формулировкой «вернуться, когда случай встретится в реальном
прогоне». Он встретился. После исправления повторный прогон таких обращений не содержит —
повода искать больше нет, — но **возможность осталась, и решение про песочницу по-прежнему
открыто**.

**Кнопки вердикта без материала бесполезны.** Экран предлагал PASS или FAIL, не показывая, на
чём это решать. Добавлены: текст задания, проверки с состоянием «до модели» и «после», вывод
каждой проверки, список изменённых файлов, патч, ответ модели и прямая подсказка, на что
смотреть. Отдельный вывод: «проверка прошла» само по себе не значит ничего — значение имеет
«до модели падала, теперь проходит».

**Fixture без интерфейса судить тяжело.** Поиск и редактор переписаны как запускаемые
приложения на чистых ES-модулях: их одинаково исполняют браузер и Node, сборки нет. Оригинал
и результат открываются рядом. Резолвер зависимостей остался без интерфейса осознанно.

## 7.2 Что дальше

**Закрыто.** Оба пункта после первого прогона — быстрая оценка «до» и «после» и шероховатости
экрана ревью — сделаны до фазы 7. `reproduction` в `benchmark.json` хранит короткий сценарий
проверки и попадает в снимок задачи. Экран ревью запускает оригинал и результат одной кнопкой,
показывает их рядом, останавливает обе стороны адресно и оставляет текстовым задачам
подсвеченный diff. Карточки свёрнуты кроме выбранной, вердикт собран в отдельный блок, а кнопка
ведёт к следующей неоценённой задаче.

## 8. Фазы

**Статус:** фазы 1–8 сделаны, фаза 9 начата досрочно: три fixture разных типов собраны в
набор `Coding General v1`. Экран прогона показывает solve rate, все исходы и средние токены с
временем на подтверждённый PASS. Следующий шаг — фаза 9.


Порядок отличается от предложенного в задании: сначала то, без чего нельзя проверить ни один
fixture, потом движок прогона. Первый настоящий fixture появляется на третьей фазе, а не на
пятнадцатой — иначе весь стек проверяется только в самом конце.

Каждая фаза заканчивается: `pnpm check`, ручная проверка, отметка в этом файле.

### Фаза 1 — Fixture как каталог ✅

- **Цель.** Fixture живёт в репозитории, а не в локальном конфиге.
- **Изменения.** `config.ts`: скан `fixtures/*/benchmark.json`, слияние со списком YAML,
  копируемый подкаталог `fixture` задан жёстко и манифестом не переопределяется.
  `shared/index.ts`: поля `hidden`, `baseline`, `limits`, проекция манифеста без секретных
  полей для всего, что уходит наружу.
- **Миграции.** Нет.
- **Риски.** Дублирование id между YAML и каталогом — падать на старте с понятным сообщением.
- **Тесты.** `config.test.ts`: скан, слияние, конфликт id, fixture без `benchmark.json`.
- **Готово, когда.** Существующие `web-app` и `node-smoke` работают как раньше, новый пустой
  каталог виден в `GET /api/fixtures`.

### Фаза 2 — Ревизия fixture ✅

- **Цель.** У каждого прогона зафиксировано содержимое fixture.
- **Изменения.** `prepareWorkspace()` возвращает `baselineTree`; engine пишет его в снимок
  промпта и в `result.json`.
- **Миграции.** Нет.
- **Тесты.** `artifacts.test.ts`: один и тот же каталог даёт одно и то же дерево дважды;
  правка файла и новый файл его меняют.
- **Готово, когда.** В `result.json` завершённой задачи виден хеш ревизии fixture.
- **Найдено по ходу.** `git add -A` уважает настройки git оператора: глобальный gitignore
  выбрасывал файлы из baseline-коммита, а `core.autocrlf` переписывал переводы строк. Файл
  при этом лежит в workspace, но ни в ревизии, ни в патче его нет. Задевало и уже
  существующий diff. Git изолирован от окружения на всех вызовах, включая запись патча мимо
  общей обёртки. Остаётся `.gitattributes` внутри самого fixture — снимается соглашением в
  документации фазы 9, не кодом.
- **Отклонение от плана.** Колонка `task_revisions.fixture_hash` осталась незаполненной.
  Ревизия задачи неизменяема и создаётся при её сохранении, а fixture правят и позже —
  записанный туда хеш устарел бы молча и выглядел бы при этом достоверным. У этой колонки
  появится владелец в фазе 5: ревизия suite фиксирует пару «ревизия задачи + ревизия
  fixture», и там же будет правило её обновления. До тех пор пишем только ревизию прогона,
  которая берётся из фактического состояния каталога в момент запуска.

### Фаза 3 — Hidden validation + baseline verification + первый fixture ✅

- **Изменения.** `engine.ts`: второй вызов `#runChecks()` по одноразовой копии результата.

- **Риски.** Fixture без зависимостей должен всё-таки воспроизводить настоящую гонку, а не её

- **Тесты.** `fixture-verify.test.ts` на fixture с заведомо падающей проверкой; проверка, что
  `validation/` отсутствует в workspace и в diff.
- **Решено: раннеру доступ к файловой системе не ограничиваем.** Песочница для `pi` — это
  отдельная работа с риском сломать обычные прогоны арены, а угроза здесь другая: модель не
  ищет ответы, она на них натыкается. Всё, обо что можно споткнуться, убрано — скрытых
  проверок нет ни в рабочем каталоге, ни в API, ни в снимке промпта. Целенаправленный поиск
  по репозиторию остаётся возможен, и это видно в логе вызовов инструментов. Вернуться к
  вопросу, когда такой случай встретится в реальном прогоне.
- **Дополнительно к плану.** Проверка «скрытые файлы не видны модели» встроена в
  `verify-fixture`: он сверяет содержимое `validation/` с рабочим каталогом и падает при
  совпадении имён. Это машинная проверка вместо строчки в документации.
- **Найдено на ревью.** Логи скрытых проверок писались в артефакты промпта, рядом с рабочим
  каталогом модели: в логе падения есть и имя теста, и текст ассерта, то есть то же самое, что
  и сам скрытый тест. Теперь одноразовая площадка скрытых проверок целиком лежит вне
  артефактов промпта, а время жизни логов задаёт вызывающий: на прогоне они исчезают вместе с
  копией, автору fixture остаются.
- **Ужесточено.** Каждая скрытая проверка обязана объявить своё исходное состояние, иначе
  конфигурация не загрузится. Без этого главный инструмент контроля качества можно было обойти,
  просто не упомянув проверку в `baseline`.
- **Готово, когда.** `scripts/verify-fixture stale-search-results` печатает
  `regression FAIL ✓`, а на каталоге `solution/` — `PASS`.

## 9. Как агент добавляет новый fixture

Контракт — один каталог, никаких правок движка.

```text
1. mkdir fixtures/<id>/
2. fixture/        — маленький работающий проект в нужном исходном состоянии
3. validation/     — скрытая проверка, воспроизводящая ровно заданное поведение
4. solution/       — эталонная правка (необязательно, но verify по ней надёжнее)
5. benchmark.json  — id, name, install, checks, hidden, baseline, preview, limits
6. scripts/verify-fixture <id>
7. создать задачу kind: coding с этим fixtureId, тегами cat:* и diff:*
8. добавить её в ревизию suite
```

Требования к качеству (§47 задания) едут в `docs/BENCHMARK-FIXTURES.md` чек-листом: баг
воспроизводится, неродственная функциональность цела, причина не помечена `TODO`, скрытый
валидатор отличает настоящую правку от обхода, исходное состояние совпадает с `baseline`.

Проверка «модель не видит скрытые тесты» автоматическая: `verify-fixture` разворачивает
workspace и падает, если в нём нашёлся хоть один файл из `validation/`.

## 10. Риски

**Зависимости fixtures — закрыт решением.** Fixtures только без зависимостей, `install` в
манифесте остаётся пустым. Прогон не ходит в сеть, копия fixture стоит один `cp --reflink`,
ревизия дерева полностью описывает условия запуска.

Цена решения: четыре задания из девяти написаны под React (1, 2, 5, 13) и требуют
переформулировки на голый DOM и TypeScript. Баг из промпта №1 от этого не страдает —
гонка «старый ответ перезаписывает новый» воспроизводится на обычном `addEventListener` и
двух промисах ничуть не хуже, чем на `useEffect`. Промпты 3, 4, 6, 7, 12 переписывать не
нужно.

Переформулировка — часть фазы 9, и в ней же проверяется, что задание осталось тем же по
сути: тип задачи, требуемое рассуждение и размер правильной правки не меняются.

**Длительность прогона.** Девять задач по десять минут — полтора часа на модель. Термозащита
(`gpuMaxTemperatureC`) может оборвать прогон в середине. Возобновление уже работает
(пропуск выполненных позиций), но проверить на реальном обрыве обязательно.

**Один воркер.** `#pump()` — единственная очередь, benchmark-прогон блокирует обычные запуски
на часы. Оставляем как есть: это честное поведение для локального железа с одной видеокартой.

**Скрытые проверки и `.gitignore`.** Если `validation/` случайно окажется внутри `fixture/`,
модель прочитает ассерты и никто этого не заметит. Отсюда автоматическая проверка в фазе 3, а
не инструкция в документации.

**Скрытые проверки видны через API и через файловую систему.** Агент работает с shell на той
же машине, где живут и репозиторий, и API арены. Значит «скрытая» проверка защищена не
изоляцией, а только тем, что модель не идёт её искать:

- API арены — закрыто в фазе 1: наружу уходит проекция манифеста без `hidden` и `baseline`,
  и в снимке промпта их тоже нет;
- файловая система — открыто, и это **уже случилось**. В первом живом прогоне модель, оставшись
  без исходного проекта, нашла его в репозитории вместе со скрытыми проверками и эталонным
  решением. `pi` запускается с `--no-approve` и без ограничения путей, каталог
  `fixtures/<id>/validation/` читается обычным `cat`. У `codex` есть `-s workspace-write`, у
  `pi` аналога в команде запуска нет. Повод искать убран, возможность осталась.

Честная формулировка того, что даёт скрытая валидация: она не даёт модели писать решение
под ассерты, которые лежат у неё перед глазами в workspace. Против целенаправленного поиска
она не защищает. Варианты по возрастанию цены: ограничить раннеру пути (у `codex` в поставке
уже есть `bwrap`), либо разворачивать рабочий каталог там, откуда репозиторий не виден.

Дешёвый промежуточный шаг, которого пока нет: после прогона искать в выводе агента обращения
к каталогам скрытых проверок и помечать такую задачу испорченной. Это не мешает искать, но
делает молчаливо недействительный результат видимым.

**Вердикт задним числом.** Авто-вердикт по исходу задачи должен пересчитываться при отметке
«не работает» — иначе `solved` разъедется со страницей результатов. Одно место расчёта,
`classifyTaskRun()`, уже есть; вердикт считать от него, а не от статуса.

## 11. MVP

Фазы 1–7 и три fixtures разных типов: правка бага (промпт №1), фича (№12 или №13),
алгоритм (№7). Этого достаточно, чтобы получить первый честный `solved / total` и понять,
стоит ли доводить suite до девяти.

Фазы 8–9 — сразу после, но прогон полезен и без них.
